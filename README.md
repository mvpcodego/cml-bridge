# Мост 1С ↔ каталог: приём обмена, сверка, выгрузка заказов

Принимает обмен из 1С по протоколу CommerceML 2 («обмен с сайтом»), складывает
каталог в базу, **сверяет его и говорит, чего в нём не хватает**, и отдаёт заказы
обратно в 1С.

Без зависимостей: только стандартная библиотека Python 3.9+. Ставить сервер базы
данных не нужно — по умолчанию SQLite, схема переносится в PostgreSQL один в один.

```bash
git clone <этот репозиторий> && cd cml-bridge
python3 run.py import tests/fixtures/import.xml tests/fixtures/offers.xml
python3 run.py report
```

Для настоящей 1С:

```bash
CML_LOGIN=1c CML_PASSWORD=секрет python3 run.py serve
# в 1С: Обмен с сайтом → адрес http://<хост>:8021/exchange, логин и пароль те же
```

## Зачем это нужно

Обмен, который «прошёл успешно», ничего не гарантирует. Инкрементальная выгрузка
**структурно не видит** архивации и удаления: товар просто перестаёт приходить,
а на сайте остаётся висеть как живой. Обратный случай тоже бывает — позиция
исчезает с витрины при исправном обмене.

У меня такой случай стоил полугода: **790 позиций не показывались на витрине**,
при этом обмен отчитывался об успехе. Причина была не в коде, а в самой модели
обмена по фильтру «изменено после». Лечилось не правкой парсера, а добавлением
периодической сверки — попутно нашлось 353 позиции с неверным остатком.

Поэтому здесь сверка — не дополнение, а главная часть.

## Что показывает сверка

Каталог того, что приехало, открывается на `/catalog` — с поиском по названию
и артикулу и карточкой позиции, где видно цены, остатки по складам,
характеристики и свойства из 1С.

`python3 run.py report` отвечает на восемь вопросов:

| Проверка | Что означает на практике |
|---|---|
| Перестали приходить из 1С | архивация или удаление, которых инкрементальный обмен не сообщает |
| Помечены на удаление | 1С передаёт это реквизитом «ПометкаУдаления», а не отдельным полем |
| Предложения без цены | нельзя продавать: клиент увидит 0 ₽ |
| Предложения без остатка | отдельно смотреть комплекты: у них остаток всегда нулевой |
| Товары без фотографий | картинки не доехали в архиве обмена |
| Один артикул у разных позиций | сопоставление по артикулу молча склеит разные товары |
| Предложения без товара | приняли offers.xml, не приняли import.xml |
| Товары без предложений | карточка есть, продавать нечего |

На публичных тестовых выгрузках 1С сверка сразу нашла то, что глазами не видно:
артикул `АРТ-88888` стоит и у «Принца (печенье)», и у «Сахарного песка»,
а `Т-123456` — у телевизоров JVC и SHARP.

## Грабли обмена 1С, которые здесь учтены

Каждая ломает обмен, при этом код выглядит правильным и ошибку не выдаёт.

**1. Кодировки разные в одном обмене.** Каталог обычно в UTF-8, а заказы 1С
выгружает в **windows-1251**. Предполагать кодировку нельзя, её надо читать из
XML-декларации. Ответы точки обмена 1С тоже читает в 1251 — отдать UTF-8 значит
получить кракозябры в служебных сообщениях.

**2. UTF-8 с BOM.** Файл, открытый как текст, начинается с невидимого символа
перед `<?xml` — парсер падает на первой строке.

**3. Пространство имён — самая тихая.** В схеме 2.07 корень объявляет
`xmlns="urn:1C.ru:commerceml_2"`, в старых выгрузках его нет. С ним имя тега
становится `{urn:1C.ru:commerceml_2}Товар`, и поиск по `Товар` возвращает пусто
**без ошибки**. Обмен отчитывается об успехе, товаров ноль. Поэтому имена
нормализуются сразу после разбора.

**4. Остатки лежат в атрибуте `КоличествоНаСкладе`**, а не `Количество`.
Парсер, ищущий `Количество`, вернёт пустые остатки — товар окажется «не в
наличии» при полном складе. Плюс узел `Склады` на верхнем уровне файла — это
**справочник** складов с адресами, а не остатки; брать его нельзя.

**5. Файл приезжает частями.** При большом каталоге 1С режет файл по `file_limit`
и делает несколько POST с одним именем. Части надо дописывать в конец, иначе
приедет только последний кусок и XML будет битым. Проверено тестом: файл,
поданный двумя половинами, собирается и разбирается.

**6. Грязь в артикулах.** В реальной выгрузке встречается `Б- 130005` — с
пробелом внутри, хотя на сайте тот же товар лежит как `Б-130005`. Поэтому для
сопоставления держится отдельный нормализованный ключ, а исходное значение не
меняется.

**7. Повторный обмен не должен делать работу дважды.** Каждая принятая часть
считается по содержимому (sha256), уже применённый файл не применяется снова.
Тот же приём в обратную сторону: заказ с существующим номером не создаёт дубль,
а отметка «выгружено» ставится только после подтверждения от 1С — если `success`
не пришёл, 1С попросит заказы снова и получит их.

**8. Многопоточность и SQLite.** Точка обмена многопоточная, а SQLite запрещает
использовать соединение из другого потока. Отсюда `check_same_thread=False`,
одна блокировка на запись и WAL — чтобы чтение отчёта не ждало идущий обмен.

**9. Символы, которых нет в windows-1251.** Знак рубля и эмодзи из комментария
покупателя обрывают выгрузку заказа на середине. Заменяются до записи.

**10. Поиск по русским названиям в SQLite.** Встроенный `lower()` приводит
к нижнему регистру только латиницу: запрос «ботинки» не найдёт «Ботинки».
Ошибки нет, просто пустой результат — для русского каталога это значит, что
поиск не работает вовсе. Регистр приводится средствами Python через
пользовательскую функцию.

**11. Битый XML не должен ронять сервис.** Приходит внятный `failure` с причиной,
обмен продолжает работать — проверено тестом.

## Что внутри

```
bridge/cml.py         разбор import.xml, offers.xml, classifier.xml, orders.xml
bridge/web.py         страницы для человека: каталог, карточка позиции, сверка
bridge/store.py       схема и запись, журнал обменов, нормализация артикула
bridge/exchange.py    точка входа для 1С: checkauth → init → file → import
bridge/orders.py      выгрузка заказов обратно в 1С
bridge/reconcile.py   сверка и отчёт
run.py                запуск: serve / import / report / order / orders
tests/test_exchange.py  сквозной тест: эмулирует 1С целиком
tests/fixtures/       публичные тестовые выгрузки 1С
```

## Тест

```bash
python3 tests/test_exchange.py
```

Эмулирует 1С и проверяет двадцать вещей: авторизацию, полный цикл обмена, приём
файла двумя частями, повторный импорт, остатки и цены, битый XML, выгрузку
заказов с подтверждением, большой каталог на 634 КБ и сверку.

## Как подключить настоящую 1С

1. В конфигурации (Управление торговлей, Управление нашей фирмой, Розница)
   открыть **Обмен с сайтом** — или в старых версиях *Обмен данными с сайтом*.
2. Создать настройку, указать адрес `http://<хост>:8021/exchange`, логин и пароль
   из `CML_LOGIN` и `CML_PASSWORD`.
3. Выбрать, что выгружать: каталог, цены, остатки, картинки; включить обратную
   загрузку заказов.
4. Запустить обмен и открыть `http://<хост>:8021/report`.

Точка обмена отвечает и по адресу `/bitrix/admin/1c_exchange.php` — это тот путь,
который 1С ожидает у сайта на Битриксе, поэтому настройку можно не менять.

## Ограничения

Сознательно не сделано: приём картинок из архива обмена (сохраняются только
ссылки), версионирование цен по типам (берётся первый тип), разбор контрагентов
из заказов. Всё это добавляется на той же схеме, но для демонстрации механики не
требуется.
